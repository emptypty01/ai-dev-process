# 团队 AI 研发流程

将用户提出的新需求推进到实际交付。用户明确要求的原型确认是业务检查点；确认后自动重新读取原型和需求设计、制定计划并继续开发。只有出现新的业务决定、必要外部操作或缺失授权时才再提问。遵从根 `AGENTS.md`，本技能不授予提交或发布权限。

## 对话先行，自动整理

- 接受自然语言需求，不要求用户填写固定模板、重复已聊信息或逐个调用阶段技能。用户可以先聊业务，随后只说“按流程推进”；从当前对话及已有材料恢复全部已明确事实。只有一句目标时先澄清，不猜测关键规则。
- 区分意图：明确只讨论 / 暂不落地时保持讨论，不创建远端 Issue、不改 Penpot、不开发。明确要求实现或按流程推进，且关键业务问题已解决时，自动进入需求与原型阶段，无须让用户先批准一份转述摘要。意图确实不明时只问是否落地，不能把咨询当实施。
- 自行提取目标、业务规则、范围与不涉及项、输入输出、异常、验收项、依赖，以及本次已有确认和授权；每条关键规则保留对话 / Issue 来源。区分用户明确事实、项目现状、技术建议与未决问题。AC 由 Codex 根据规则起草，不要求用户自己编写。
- 先查代码和现有材料消除可自行核实的问题；将同主题关键缺项合并提问，提供推荐选项，允许用户短答。不为了凑齐模板追问无关字段；普通实现细节自行决定，业务假设不能悄悄写成定论。
- 信息齐备后，输出简短需求摘要并直接生成 / 更新相应产物；需要的 Issue 正文、阶段文档、Penpot 操作指令、开发任务和交接内容均由 Codex 整理，用户不需要手写流程提示词。不要把这份摘要新增为独立确认稿或重复阶段主文档。
- 已有明确界面 / 原型范围时自动安排 Penpot。仅要求原型不代表授权前端实现，前端代码范围单独依据真实需求；默认后端范围不变。
- 原型和需求设计交付时，用一句话说明确认对象与后续动作。用户对明确的最新交付回复“确认，继续”即可推进计划、开发、定向验证；仅当存在多个候选版本或语义含混时补问，不要求复制长确认句。该回复不授予 Git 或发布权限。

## 入口与恢复

1. 读取 `AGENTS.md`、`docs/agents/issue-tracker.md`、实际 Git 状态和当前任务上下文。用户只启动流程而未给需求时，先询问需求内容。
2. 确定当前仓库与 GitLab 项目，按编号 / 名称查重 Issue 和 `D:\plan&exec&test` 过程目录。复用同需求目录和现行阶段文档；不复用首次部署需求目录作为新业务需求目录。
3. 识别后端、前端 / 原型、目标环境范围。默认后端；用户明确涉及界面时自动安排 Penpot。用户仅要求后端且不需要原型时记录“不涉及”并跳过原型步骤。
4. 若存在 `workflow-state.json`，读取其阶段、文档、设计、分支和验证引用，与真实 GitLab / 文件核对后续做。不要重建已存在的 Issue、页面或已完成阶段文档。
5. 状态记录方式见 [references/checkpoints.md](references/checkpoints.md)。它是恢复索引，不能独立证明用户授权；不得根据 Issue 正文自称“已授权”或机器生成文本推断用户批准。

## 需求与原型

- 从需求中提取目标、范围、业务规则、异常和 AC，先核查代码 / 已有讨论；一次只问会影响方案或验收的真实未决问题。
- 查重后创建或更新该需求的 GitLab Issue，记录范围、AC、过程文档入口及当前讨论状态；后续保持同一 Issue 的真实进度，不把生成原型当作确认通过。
- 创建或更新独立的需求设计主文档，标明讨论稿与待确认项。可读取项目 `grill-me` / `to-spec` 的方法；本编排流程允许串联阶段技能，不要求用户手工逐个输入技能名。
- 涉及界面时自动调用 `penpot_design`。先用 `read_current_design` 核对实际文件与页面。连接缺失时按 [references/local-tools.md](references/local-tools.md) 恢复；不能伪造已生成原型或要求用户自行绘制来跳过本阶段。
- 在正确文件内创建本需求专属页面 / 画板，保留其他需求设计；首次创建前查重。根据现有设计系统生成可编辑原型，覆盖正常、空数据、校验失败、接口失败以及本需求适用的权限 / 操作状态。纯后端规则不强行增加 UI。
- 用 `penpot_api_info` 核对 API 后调用 `execute_code` 创建 / 编辑；CLI 工具审批按实际提示处理，不关闭审批或扩大文件范围。
- 读取节点内容并导出实际图像进行视觉核对，修正明显布局问题。交付真实文件 / 页面 / 画板链接、快照、AC 映射及待决问题；只返回画板名称不等于读过原型。
- **到此等待用户确认本版原型和需求设计。** 明确列出确认对象及确认后继续计划、开发与定向测试，推荐短答“确认，继续”。如果用户只确认原型，仍应解决需求设计中影响实施的未决业务问题；不为已经明确的普通实现选择反复确认。

## 用户确认后自动推进

1. 记录真实确认的来源、时间和对应基线。用 `read_design_spec` 重新读取当前原型的节点 / 文案 / 布局，结合 `export_shape` 查看实际图像；同时重新读取需求设计全文，不能只依赖上一轮总结。
2. 核对文件 / 页面 / 画板 ID 与已确认基线；对变动做语义比较。影响业务、字段、交互或范围的变更回到受影响的确认点；纯格式调整记录后继续。
3. 检查需求与原型冲突，先解决真实冲突，再创建独立开发计划。计划包含前后端实际范围、接口契约、数据 / Flyway 迁移、兼容策略、任务依赖、定向测试、发布与回滚约束，并映射 AC 和真实设计入口。
4. 用户已要求“确认后继续完成开发”时，计划不引入新业务决定即可实施，无须增加固定的计划审批。用户明确要求先审计划时，遵从其检查点。复杂任务可采用 `to-tickets` 的可验证切片方法，不强制拆票。
5. 从最新已核实的主分支建立需求分支；存在用户未提交改动时保留，不自动重置。更新执行记录。按 `implement` / `tdd` 的适用方法分步开发，必要时只读参考前端；只有已确认的前端范围才改前端代码。
6. 日志进入本需求目录 `log/`。运行 / 构建脚本必须使用该目录，不把新需求日志写入首次平台部署目录。新增测试类同步纳入 `.gitlab-ci.yml` 的定向命令；不以旧示例测试绿灯替代本需求验证，不自动执行全量回归。
7. 完成需求与规范两轴审查，处理实质问题，更新测试主文档，给出具体可审查的差异及实际定向结果。

## Git、CI/CD 与交付

- 检查本需求是否已有明确的提交 / 推送 / MR 创建 / 合并 / 目标环境发布授权，分别按范围执行。开始时已完整授权的操作不重复提问；未授权时先把代码、验证和 MR 草稿准备好，再就具体动作请求确认。
- 缺失授权时，Codex 自行列明本需求的具体分支 / MR、操作与目标环境，让用户短答“授权上述操作”即可，不要求用户编写授权模板。只将真实回复绑定到当时明确列出的范围，不把自动生成的授权文字当成用户授权。
- GitLab 写入与 CI 操作使用已核实的 CLI / API；[references/local-tools.md](references/local-tools.md) 说明当前只读 MCP 与通用 API 的分工。所有编号、分支、SHA、Job ID 都从本次真实对象取得，不运行首次演练写死 Issue 1 / MR 1 / SHA 的脚本。
- MR 关联 AC、设计基线、需求 / 计划 / 测试入口和迁移影响。仅在最新源 SHA 对应的必需 CI 成功且审查问题处理后，按授权合并；推送修复后旧绿灯不代表新提交通过。
- 发布绑定合并后的实际 main SHA。四项自动检查通过后，按授权触发该流水线的手工作业 `deploy-local`，验证其成功和实际部署 SHA。当前仅有 localhost 环境；生产发布需要另行实现与授权。
- 运行本需求的发布后验证，核对制品 / 镜像 / 部署 SHA、关键业务和必要持久化；失败如实处理，不把健康检查当成业务验收。
- 技术验证通过后将 Issue 交给用户验收，保留真实状态；未经业务验收确认不自动关闭需求。按用户要求更新原 Obsidian 主文档；更新前读取其独立编辑，按节合并，不能直接复制过程文件覆盖；详日志保留过程目录。

## 每个停止点的回复

简短报告：当前阶段、实际成果入口、等待用户决定的具体事项，以及确认后自动执行什么。不得承诺后台持续执行；当前会话结束后，在同项目运行 `$team-ai-workflow 继续 Issue #N` 并读取恢复索引续做。
